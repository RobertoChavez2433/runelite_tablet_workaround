## Review Notes

Five items changed during implementation. Each is documented where it appears; collected here for handoff clarity.

1. **Jar deploy via APK extract, not base64 stdin.** Draft W4 called for `TermuxCommandRunner.execute(..., stdin=base64EncodedJar)`. Real-world test hit a 30s RUN_COMMAND IPC timeout on the 347KB base64 payload (either Binder parcel size or Termux service-side stdin buffering). Switched to `unzip -p "$APK" assets/libs/<jar>` against `pm path com.runelitetablet` — works because APKs at `/data/app/…` are world-readable on Android 10+. Deploy time dropped from 30s timeout to 141ms. Same pattern is reusable for any future asset too big for stdin.

2. **UI scale: Kotlin-computed, not shell-computed.** Draft had the launcher read `wm size` for adaptive scaling. `wm size` fails from `run-as com.termux` with "Can't find service: window" (Binder permission), and `xdpyinfo` isn't in the base Termux package set. Moved the computation to `LaunchCoordinator.computeUiScale()` which reads `context.resources.displayMetrics` (works from any UID) and passes the result via `RLT_UI_SCALE` env to the script. Memory `feedback_no_hardcoded_ui_sizes.md` codifies the "no hardcoded sizes" rule — breakpoints are 1.0 / 1.5 / 2.0 / 2.5 at 0 / 1800 / 2400 / 3200 pixels respectively.

3. **Termux:X11 resolution needs pre-fork setting + `adjustResolution:true`.** Draft assumed setting `displayResolutionMode:native` anywhere in the launcher would work. Reality: Termux:X11 reads the pref ONCE at server start, and on HiDPI panels `native` falls back to DP-based half-resolution unless `adjustResolution:true` also tells it to resize the X canvas to the surface size. Moved the pref broadcasts to BEFORE `$TERMUX_X11_BIN :0 &` and added `adjustResolution:true`. Before this fix the X graphics device came up at 1480×924 (half of physical 2960×1848); after, the 2× `sun.java2d.uiScale` transform lands on effective 2960×1848.

4. **GPU plugin fb-config blocker identified, not resolved.** R3 FPS A/B is explicitly deferred — the Phase 3 exit criteria allow this per the original plan when a specific blocker is identified. Added debugging env (`MESA_EXTENSION_OVERRIDE=-GL_ARB_depth_clamp,-GL_EXT_depth_clamp`, `MESA_GLSL_CACHE_DISABLE=0`, `MESA_GL_VERSION_OVERRIDE=4.3COMPAT`) and a 0.5s post-socket settle; neither fixed it. Follow-up task: run `glxinfo -B` on device to enumerate what virgl exposes, then either tweak rlawt's FBConfig attr list or relax Mesa's picker.

5. **RuneLite launcher `--scale` flag is launcher-only, not client-main-class-accepted.** Draft tried passing `--scale 2` as a client arg. joptsimple rejected it with `UnrecognizedOptionException: scale is not a recognized option`. Root cause: `RuneLite.jar` is a Swing launcher wrapper; its `--scale` flag affects the launcher's own bootstrapping logic and isn't a RuneLite-client option. Since our path invokes `net.runelite.client.RuneLite` directly (no launcher), we use `-Dsun.java2d.uiScale=$UI_SCALE` instead — same runtime effect on AWT HiDPI scaling without the wrapper.
